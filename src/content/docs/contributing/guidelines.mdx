Packagers and maintainers MUST follow the policies and guidelines listed in this document.
Everything covered here is one of 3 things:

- Differences from the [Fedora Packaging Guidelines]
- Changes in addition to the [Fedora Packaging Guidelines]
- Terra-exclusive guidelines

It is highly recommended to read through the [Fedora Packaging Guidelines] on languages/sections not listed here, or for greater detail.

## Terra Packaging Guidelines

### Usage of the `lld` Linker

Terra uses [`lld`](https://lld.llvm.org/), LLVM's linker, as the default linker for Rust and Nim packages.
It is significantly faster than GNU `ld` and, since the Rust toolchain is built around LLVM, more reliable for Rust builds than other alternative linkers.
You MAY enable it in C/++ projects by adding `-fuse-ld=lld` in `CFLAGS`/`CXXFLAGS`/`LDFLAGS`. 
You can do this by adding `%global _pkg_extra_ldflags -fuse-ld=lld` in your spec.

`lld` is enabled by default for Rust packages on Fedora via the `%__terra_use_lld` macro in `anda-srpm-macros`. `lld` is also preinstalled in the builders (see [terrapkg/builder](https://github.com/terrapkg/builder)).

You can disable `lld` for Rust by adding `%global __terra_use_lld 0` to your spec file.

<Aside type="caution">
`mold` was previously Terra's default linker. Packages SHOULD NOT add new `mold` build dependencies; use `lld` instead.
</Aside>

## Declarative Builds

<Aside type = "caution">
  EL10 is on RPM 4.19, which doesn't support declarative builds. If you want your package to work in EL10, don't use this!
</Aside>

Starting in RPM 4.20, you can declare a <Code code={`BuildSystem:`} lang={RPMSpec} inline /> in your spec file to automatically populate the following RPM spec sections:

```rpmspec
%prep
%generate_buildrequires
%conf
%build
%install
%check
```

There are cases where <Code code={`%prep`} lang={RPMSpec} inline /> is not defined, due to [BuildSystem Global Defaults](https://rpm-software-management.github.io/rpm/manual/buildsystem.html#global-defaults).

Note, this does **not** populate <Code code={`%description`} lang={RPMSpec} inline />, <Code code={`%files`} lang={RPMSpec} inline />, <Code code={`%changelog`} lang={RPMSpec} inline />, or any of the preamble tags.

For more information on using a declarative build, the [upstream docs](https://rpm-software-management.github.io/rpm/manual/buildsystem.html) are a great reference.

Currently, Terra supports all <Code code={`BuildSystem`} lang={RPMSpec} inline />s that Fedora does, except <Code code={`BuildSystem: cargo`} lang={RPMSpec} inline />.

A (potentially non-exhaustive) list of <Code code={`BuildSystem`} lang={RPMSpec} inline />s supported in Fedora:

- cmake
- gap
- maven
- dune
- topkg
- meson
- tree_sitter
- pyproject
- rebar3
- cargo (NOT supported in Terra, see below)

Terra's `anda-srpm-macros` currently provides the following <Code code={`BuildSystem`} lang={RPMSpec} inline />s:

- [terra_cargo](/contributing/langs/rust#buildsystem-terra_cargo)
- [nimble](/contributing/langs/nim#buildsystem-nimble)
- [terra_cabal](/contributing/langs/haskell#buildsystem-terra_cabal)

## Shell Completions

- Each shell completion file SHOULD be in its own subpackage.
- SHOULD use the [`%pkg_completion` macro](/contributing/srpm#pkg_completion).
  - Currently supported shell completions:
    - bash
    - elvish
    - fish
    - nushell
    - zsh

## Development and Shared Libraries

You SHOULD try to use the [`%pkg_devel_files`, `%pkg_libs_files` and `%pkg_static_files` macros](/contributing/srpm#subpackages).

Shared library packages SHOULD be suffixed with <Code code={`-libs`} lang={RPMSpec} inline />.
These packages SHOULD NOT contain anything **except**:

```rpmspec
%_libdir/*.so.*
%doc …
%license …
```

<Aside type="caution">
  Do not confuse the `-libs` file (`*.so.*`) with a `-devel` file (`*.so`).
</Aside>

Development library packages SHOULD be suffixed with `-devel`.
These packages SHOULD NOT contain anything **except**:

```rpmspec
%doc …
%license …
%_includedir/*
# ^ source files, depending on the language, could be in other locations
%_libdir/*.so
%_libdir/*.a
%_libdir/pkgconfig/%{name}.pc
# and other development files (.vapi, .typelib, .gir, etc.).
```

## %changelog

You MUST add a Changelog entry when you submit a new package, and you MUST NOT use `%autochangelog`.
We typically use `Initial package`/`Initial commit`, but anything that describes adding the package is fine. Please note that to refer to a macro in a changelog entry, you MUST escape it with two `%%`, like so: `- Added %%make_install`

### Changing an Existing Package

You SHOULD add a <Code code={`%changelog`} lang={RPMSpec} inline /> entry for large changes, such as file renames, new build process, etc.
Small changes like adding build dependencies or adding one-liners to make a build work MAY be omitted from adding a <Code code={`%changelog`} lang={RPMSpec} inline /> entry, it is up to you.
If it is a substantial change, please note this is valid syntax:

```rpmspec
%changelog
* (date name email version)
- Change 1
- Change 2
- Change 3
- Change 4
```

### Copying a Spec from a Different Repository

When copying/porting/using a spec file from a different repository (SUSE, Mandriva, RPMfusion, Copr, etc.), you MUST preserve any changelogs in the spec, and then add your own changelog entry as `Port to Terra`.
You MAY specify which repo it has been ported from (`Port to Terra from X repo`).

### Modifying Changelog Entries

This _should_ not need to be done, the only reasons are if there is a formatting error, date error, spelling mistake, or updated name/emails.
It is also acceptable to add more to previous changelogs (for example, adding missing emails/version), but there has to be a reason to do this (Don't open a PR editing a changelog because you are bored).

## Fixing Packages

- If a PR is changing anything user-facing, the <Code code={`Release:`} lang={RPMSpec} inline /> tag SHOULD be bumped. The only exception SHOULD be if you are fixing a package where the current version does not and has never built.
  - Some (not all!) examples of user-facing fixes requiring a <Code code={`Release:`} lang={RPMSpec} inline /> bump:
    - Installing a missing file.
    - Adding any build or non-build, hard or soft, forward or backward dependencies.
    - Changing any user-facing tags (<Code code={`URL:`} lang={RPMSpec} inline />, <Code code={`License:`} lang={RPMSpec} inline />, <Code code={`Summary:`} lang={RPMSpec} inline />, etc.).
- If a package fix PR is _not_ fixing/changing anything build-facing, the <Code code={`Release:`} lang={RPMSpec} inline /> tag SHOULD NOT need to be bumped.
  - Some (not all!) examples of changes which **don't** require a <Code code={`Release:`} lang={RPMSpec} inline /> bump:
    - Fixing a package that failed to build when the <Code code={`Version:`} lang={RPMSpec} inline /> tag is bumped.
    - Clarifying/editing a comment within a spec
    - Any changes that do not affect the final package.
- If you are unsure if a bump is needed, bump it.
- Follow appropriate changelog procedures outlined in the above section.

## Patches

We generally follow the [Fedora patch guidelines](https://docs.fedoraproject.org/en-US/packaging-guidelines/#_applying_patches). However, we encourage the use of [%autopatch](https://developer.fyralabs.com/rpm/macros#autopatch) instead of [%patch](https://developer.fyralabs.com/rpm/macros#patch) for simplicity purposes, but if it doesn't work for your patch usecase you MAY use `%patch` instead.

## Providing Your Own .desktop File

If you are packaging a graphical app that doesn't provide its own `.desktop` file, you SHOULD create one.

### Creating the .desktop File

Copy the following template:

```
[Desktop Entry]
Name=PACKAGE NAME
Exec=PROVIDED_BINARY
Icon=ICON NAME
Type=Application
```

The `Icon` tag SHOULD NOT a contain full path, just the name of the icon file **without** the file extension.
The `Exec` tag SHOULD be a full path if the binary placed in `/usr/bin` is a symlink.
If this is not the case, it is up to you if you want to use the full path or not (it will look in the user's `$PATH`).

You SHOULD name this file either `package-name.desktop` or `package_app-ID.desktop`.
You MAY add more tags, to see all possible tags, read through the [freedesktop specification](https://specifications.freedesktop.org/desktop-entry/latest).

### Installing the .desktop File

To install the `.desktop` file:

1. Add it to your package's folder
2. Add it as a <Code code={`Source:`} lang={RPMSpec} inline /> in the .spec file
3. Install it
4. List it in the <Code code={`%files`} lang={RPMSpec} inline /> section

It is RECOMMENDED to use the [`%_appsdir` macro](/contributing/srpm#_appsdir) instead of `%_datadir/applications/`, and to use the [`%desktop_file_install` macro](/contributing/srpm#desktop_file_install).
With [NeoHtop package] as the example:

```rpmspec
Source1:  NeoHtop.desktop

...

%install
%desktop_file_install %{SOURCE1}

...

%files
...
%{_appsdir}/NeoHtop.desktop
```

### Validating the .desktop File

You MUST validate your `.desktop` file. To do this, add the following to your spec file:

```rpmspec
BuildRequires:  desktop-file-utils

...

%check
%desktop_file_validate %{buildroot}%{_appsdir}/NeoHtop.desktop

...
```

### Finished Example

`NeoHtop.desktop`:

```
[Desktop Entry]
Categories=Utility;
Comment=A cross-platform system monitor
Exec=NeoHtop
Icon=NeoHtop
Name=NeoHtop
Terminal=false
Type=Application
```

All custom `.desktop` file portions of a spec file:

```rpmspec
Source1:  NeoHtop.desktop

...

BuildRequires:  desktop-file-utils

%install
...
%desktop_file_install %{SOURCE1}

%check
%desktop_file_validate %{buildroot}%{_appsdir}/NeoHtop.desktop

%files
...
%{_appsdir}/NeoHtop.desktop
```

## Usage of %elifarch

To make specs easier to read, you SHOULD use <Code code={`%ifarch`} lang={RPMSpec} inline /> followed by <Code code={`%elifarch`} lang={RPMSpec} inline /> before <Code code={`%endif`} lang={RPMSpec} inline /> in specs where build steps are arch dependent.

<CardGrid>
  <Card title="Incorrect:" icon="error">
    ```rpmspec
    %ifarch x86_64
    %define arch %{nil}
    %endif
    %ifarch aarch64
    %define arch arm64-
    %endif
    ```
  </Card>
  <Card title="Correct:" icon="approve-check-circle">
    ```rpmspec
    %ifarch x86_64
    %define arch %{nil}
    %elifarch aarch64
    %define arch arm64-
    %endif
    ```
  </Card>
</CardGrid>
